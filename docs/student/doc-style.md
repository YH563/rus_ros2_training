# 文档规范

> 本文件规定「任务文档、Issue、PR 描述」怎么写。代码规范见 [`cpp-style.md`](cpp-style.md)。

## 1. 基本约定

- 中文写说明，命令、代码、路径、变量名保持英文
- 一个文件一个主题；标题层级从 `#` 开始，不跳级
- 命令块标明语言（`bash`、`cpp`、`yaml`、`text`），保证可直接复制
- 链接用相对路径，不写本机绝对路径（如 `/home/xxx`）
- 不写「大概」「可能」这类模糊要求；验收必须能执行、能判断通过与否

## 2. 文件命名

| 类型 | 规则 | 示例 |
|---|---|---|
| 普通文档 | 小写 + 连字符 | `linux-basics.md` |
| 任务文档 | `NN-英文短名.md` | `01-nodes-and-topics.md` |
| 代码目录 | 小写下划线包名 | `training_pubsub` |

## 3. 链接

- 同目录：`[faq.md](faq.md)`
- 上级目录：`[根 README](../../README.md)`
- 代码目录：`` [`src/training_pubsub`](../../src/training_pubsub/README.md) ``
- 提交前检查：链接目标存在，重命名文件时同步改所有引用

## 4. 任务文档模板

每个 `tasks/NN-*.md` 必须包含以下小节，顺序固定：

```markdown
# Task NN：标题

| 模块 | 预计时间 | 前置 | 分支 |
|---|---|---|---|

## 1. 学习目标
## 2. 交付物
## 3. 骨架说明（可改 / 不可改）
## 4. 验收（命令 + 预期输出）
## 5. 约束
## 6. 提示（1 文档 / 2 API / 3 仅口头）
## 7. 自检清单
## 8. 完成定义（DoD）
## 9. 提交要求
```

要求：

- **验收命令**必须能从干净终端复制执行，带预期结果
- **约束**写清哪些文件不能改、能不能加依赖
- **提示**分三级，第三级不写进仓库，只在 review 评论给
- **DoD** 用可判断的句子，不写「基本完成」

## 5. Issue 写法

Issue 与任务文档同源，至少包含：

- 模块、任务文档链接、分支名
- 目标（一句话）
- 验收命令（从任务文档复制）
- 约束（从任务文档复制）
- 只放提示 1、2

任务要求变了：先改文档，再改 Issue，避免两处不一致。

## 6. PR 描述

- 关联 Issue：`Closes #12`
- 改了什么：3 行以内
- 数据流：谁发布 → 哪个话题/服务 → 谁订阅/调用
- 自测命令与关键输出（不要只写「已测试」）
- 仍未解决的问题（没有就写「无」）

## 7. 审查友好

- 一次 PR 只做一课，控制在 300 行以内
- 不提交调试残留、注释掉的代码、`build/install/log`
- 命名和术语与任务文档一致（`publish_rate_hz` 不要写成 `rate`）
- 大段生成代码或日志不要贴进 PR，给关键几行即可

## 8. 交付前检查

```bash
# 链接是否断了（用编辑器或脚本检查）
grep -rn '](.*\.md)' docs/student/
```

- [ ] 标题层级正确，没有跳级
- [ ] 命令可复制执行
- [ ] 相对链接有效
- [ ] 没有本机绝对路径
- [ ] 验收标准可判断
